# Verificador independente — instalar fora do repositório de produto
Este é um kit de referência testado localmente, não um pipeline configurado. `gov.py`, `verifier.py`, `mcp_verifier.py` e políticas precisam ser copiados para um repositório/control plane separado, cujo acesso de escrita é da raiz. Executor não recebe segredo de assinatura, token de tag, configuração do verificador nem admin. `trust.example.json` é só modelo; root define e aprova os valores reais fora da árvore do executor. Crie três identidades (executor/revisor/verificador) e uma raiz; GPG fingerprints públicos únicos. Provedores de executor e revisor diferentes. `identities.yaml` só muda por root-signed bootstrap. Fixar commit inicial root-signed e fingerprints em trust externo (arquivo só-leitura para executor). Não reutilizar as keys descartáveis dos testes.

## Enforce no GitHub (R0-03/R0-06)
1. Repositórios privados `loyalty-news` (produto) e `loyalty-news-governance-verifier` (verificador), ou organização com política equivalente. Conferir recursos do plano; rulesets para repos privados podem depender de plano. Se não houver enforcement verificável, bloquear. Root é admin, executor só branch/PR; reviewer pode revisar/assinar parecer mas não editar critério/verificador; verificador só leitura de produto e criação dos refs reservados via GitHub App de privilégio mínimo, sem alteração de policy.
2. Ruleset main: exigir PR, checks obrigatórios de app/runner confiável externo, sem force push, sem bypass executor, merge automático só após checks e aprovação automática independente. Rulesets de tags `gate/*`, `task/*`, `review/*`, `checks/*`, `release/*`: restringir criação a identidade autorizada, negar atualização/exclusão; não permitir que executor mude configuração. Proteção efetiva do código externo, lista de paths, settings Claude, branch e tags é pré-condição. Documentar tentativa real negativa e log de audit. Não confiar em check definido no PR ou status com nome arbitrário. Verificar se configuração em org/Enterprise é necessária.
3. Root-signed commit do baseline e trust map com `protected` exato de `governance/policy.json`, acrescido dos caminhos do pipeline externo. Config do verifier root-only, revisão de alterações de política assinada da raiz e pareceres conforme norma. O verificador pinado **não importa módulos do checkout de produto**; clone limpo, chaveiro público aprovisionado externamente, Git/GPG binaries confiáveis, sem hooks ou config do executor; não confiar em refs não vindos do remote protegido.
4. Runner de checks em container/VM descartável sem segredos, token de escrita, docker.sock ou rede de saída, com workspace isolado e policy de testes root-only. Rodar `clean_checks.py` com commit exato, checks allowlist e output fora da árvore; montar policy somente leitura. Exemplo `checks.example.json` só para R0-05; criar os demais checks executáveis independentes e validar cada um. Não executar `pull_request_target` em código não confiável com credenciais. A saída JSON deve ser transferida por canal autenticado do job confiável (run/commit/checksum/proveniência), nunca por upload do executor. O runner não assina.
5. Job reviewer independente: prover evidence bundle do commit e critérios a outro provedor autenticado, guardar logs saneados (provider/model, request ID e versão do prompt) e parecer. Assinar tag anotada `review/<TASK>/<COMMIT>` **com chave do revisor** e mensagem JSON com `id`, `commit_sha`, `decision: favorable`, `executor_provider`, `reviewer_provider`, `executor_fingerprint`, `reviewer_fingerprint`; sem tag por mera autodeclaração de LLM. Evidência assinada do provedor precisa ser revisada R0-06. Identidade do executor e revisor distintas. Se inconclusivo, bloquear.
6. Job signer separado, sem execução de código do produto, valida proveniência do check do runner externo, esquema, commit, hashes, lista de testes e integridade; só então mesma identidade verificadora assina anotação `checks/<TASK>/<COMMIT>` usando JSON produzido pelo runner (`id`, `commit_sha`, `clean_environment`, `runner_policy_sha256`, `tests`). Nenhum input de executor pode escolher comando, resultado ou forjar attestation. `verifier.py` verifica essas assinaturas e refaz critérios. Se falta check, confiança ou review não favorável, rejeitar. Logs de falha sem dados secretos.
7. A partir do checkout limpo do commit `TARGET`, chamar no runner confiável: `python3 /trusted/verifier.py --repo /clean/product --trust /trusted/trust.json gov_accept_gate R0-01` ou `... gov_accept_gate R0`. O método refaz checks estáticos dos artefatos, tags, P0, paths protegidos, deps; assina `task/<id>/accepted` ou `gate/<wave>/accepted` local. Push autenticado somente da referência específica validada pelo pipeline (não `git push --tags`), depois confirmar tag remota. Em falha, tag assinada `/rejected/<commit>` sem overwrite. O código não efetua push automaticamente. Signer key no cofre com escopo mínimo, nunca no ambiente de teste/revisor/executor. Não assinar gate R6 antes do delta V21-05. Não escolher provedor/modelo sem teste R2-07.
8. Opcional: `acceptance_dir` externo mantém espelho de records assinados. Tag é fonte de verdade; arquivo espelho não tem poder de aceitar. Para norma estrita `governance/acceptance` no produto, ratificar delta V21-06. `mcp_verifier.py` é stdio exclusivo do pipeline; não declarar no `.mcp.json` do executor.
9. Prove todos os casos §9 do caderno de auditoria no ambiente real, principalmente 8/13 (rule enforcement, não só diff) e 12 (origem do provedor), mais bootstrap, rollback, concorrência entre branches, recuperação de claim órfã, revogação/rotação de keys. Até essa prova, F-120 aberto, nenhuma tag válida de produção, R0 não homologada. O código local não fecha a brecha de admin do GitHub. Atualizar lista de checks e trust root-only conforme aprovação; nunca entregar segredo ao Claude.

## Limites
Sem pipeline real, sem signer remoto, sem serviço de provedor/revisor conectado, sem atestação de ambiente limpo de GitHub ou testes de 87 outras tarefas. Checks report + assinaturas são a interface, não prova espontânea. O tool `clean_checks.py` valida cwd/ambiente básico mas não fornece isolamento OS por si só: usar sandbox real. Sem chave privada não existe aceite válido. O release gate exige prova remota. Encerrar achados exclusivamente por evidência e tag verificadas.
